# 提取任务

从下面的执行日志段落中提取 GTD 清单条目。

## 输出格式

以 JSON 格式输出，格式如下：

```json
{
  "items": [
    {
      "title": "条目标题（短语即可）",
      "description": "条目描述（提取关键信息，简洁）",
      "category": "下一步行动 | 等待回复 | 悬而未决 | 日程",
      "priority": "高 | 中 | 低",
      "needs_discussion": false
    }
  ]
}
```

## 分类规则

- **日程**：有明确日期/时间安排的事项。注意：日程会议中的子任务/准备工作应归入"下一步行动"而非"日程"
- **下一步行动**：自己可以推进的具体任务，不需要等待他人。有明确所有者和执行路径
- **等待回复**：需要等待他人回应或行动的事项。特征是"等某人做某事"
- **悬而未决**：有想法但尚未决定如何推进，或属于方向性/策略性的思考，没有明确的下步动作

典型错误：
| 原文 | 不应归类为 | 应归类为 |
|---|---|---|
| "半个月内要再接一个新单"（方向性目标，无明确执行路径） | 下一步行动 | 悬而未决 |
| "告诉他去 review，然后交付"（等对方做） | 下一步行动 | 等待回复 |
| "周四开会，会上处理"（会议本身的子议题） | 下一步行动 | 日程 |

## 优先级规则

- **高**：重要且紧急，或对业务有重大影响
- **中**：重要但不紧急，或常规工作
- **低**：想法性质、探索性质，或时间上不紧迫

## 时间感知

日志段落按时间顺序排列，同一篇日志可能包含「计划 → 执行 → 已完成」的演进。

判别规则：
1. **已完成的不列入**：过去时 / "已..." / "...过了" / "审计过了" / "已经..." → 已完成的动作，**不应列为候选条目**，也不标记 needs_discussion。完成了就是完成了
2. **决定不做的不列入**：原文明确说"不需要" / "不咋需要" / "先那样" → 已决策跳过的事项，不要列为候选
3. **纯观察不列入**："看起来..." / "确实..." / "对，因为..." → 这是结论/感慨，不是待办
4. **不确定 vs 已完成的边界**：如果你判断某件事"可能已经做完了"，倾向跳过而非标记讨论。needs_discussion 只用于"这件事看起来是待办，但我拿不准分类或优先级"的情况

## 注意事项

- 一条日志段落可能包含多个条目，也可能没有条目
- 标题要具体，便于后续识别和追踪
